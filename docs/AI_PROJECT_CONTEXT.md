## 1. Для чего нужен проект

Yugra18 — веб-платформа анализа, сравнения и сценарного прогнозирования социально-экономической устойчивости 22 муниципальных образований ХМАО — Югры. Целевые пользователи — специалисты регионального Департамента экономического развития и муниципальных администраций.

Основные функции: карта и паспорта муниципалитетов, сравнение территорий, каталог и матрица статистических данных, объяснимый мониторинг рисков, конструктор отчётов и концептуальные сценарные расчёты на 1–3 года.

Культурное оформление вдохновлено орнаментами ханты и манси. При инженерных изменениях дизайн по умолчанию сохраняется.

## 4. Supabase: критический migration drift

Подключённый проект: `dmbikidqikjupkghywbz`, PostgreSQL 17.11, статус ACTIVE_HEALTHY.

На проверке 18.11.2026:
- В репозитории было 110 SQL-файлов миграций.
- В production `supabase_migrations.schema_migrations` — 96 зарегистрированных версий; последняя `20261107055919`.
- В Git обнаружены четыре повторяющихся version prefix: `20261030194500`, `20261030200000`, `20261030201500`, `20261030203000`.
- Есть SQL-файлы, отсутствующие в production migration history, и зарегистрированные production-версии без файла с тем же version prefix в текущем репозитории.
- В частности, `20261107114255_harden_external_rating_review_default.sql`, `20261107122134_allow_cross_source_staging_import.sql` и `20261118033000_harden_staging_import_integrity.sql` есть в Git, но не зарегистрированы как применённые в production на дату проверки.
- `20261118033000` проходила тестирование на live PostgreSQL в транзакции с ROLLBACK; это не означает, что миграция применена.

**Не исправляй это переименованием/удалением старых файлов или слепым `supabase db push`.** Сначала построй таблицу соответствия «файл → version prefix → production history → checksum/содержание → зависимые миграции». Подготовь безопасный forward-only план. Не повторяй data imports и не меняй production без явного разрешения пользователя.

## 5. Методологические и информационные ограничения

1. Подтверждённая статистика должна иметь первоисточник, источник/URL, код и определение показателя, единицу, год, период, уровень географии и статус проверки.
2. Не объединяй записи разных уровней географии. Значение поселения не является значением муниципального района.
3. Не заменяй пропуск нулём; не усредняй конфликтующие значения; не соединяй разные единицы, определения или периоды.
4. Номинальные денежные значения не называй реальными без дефлятирования. Накопительные Q1/H1/Q3/annual срезы нельзя складывать друг с другом.
5. «Если быть точным»/БД ПМО может быть обработанной копией исходных статистических данных, а не независимым подтверждением от Росстата.
6. РИА Рейтинг — внешний бенчмарк; много результатов имеют региональный уровень. Региональный результат нельзя назначить муниципалитету.
7. Риск-модель должна быть fail-closed: отсутствие данных или неоднозначное направление не может давать ложный зелёный статус. Показывай достаточность покрытия и доказательства негативных сигналов.
8. Кандидатный шестинаправленный индекс не является официально утверждённым индексом до появления утверждённой методики и валидации.
9. Сценарные значения — условный расчёт на базе входных допущений. Не называй его статистически обученной моделью или официальным прогнозом без доказательств.
10. Причинный эффект мер поддержки нельзя заявлять на основе простой динамики «до/после» без подходящего исследовательского дизайна и контрольных данных.

## 6. Команды и критерии проверок

Текущие команды `package.json`:
- `npm ci` — установка lockfile-зависимостей.
- `npm test` — основной Node QA/regression набор.
- `npm run build` — production-сборка.
- `npm run check:map-coverage` — проверка покрытия карты.
- `npm run check:risk-pilot-csv` — аудит пилотного CSV.
- `npm run validate:rosstat-crosswalk` — проверка справочника муниципалитетов Росстата.

Отдельного `lint`-скрипта в текущем `package.json` нет. CI также выполняет отдельный PostgreSQL migration integration workflow на disposable тестовой схеме. Успех integration CI не доказывает применение миграции к production Supabase.

Перед завершением работы проверяй production build, regression tests, migration integration, diff и актуальную ветку. В отчёте разделяй GitHub CI, Vercel Preview, Vercel Production и Supabase Production.
