# Yugra18 — пользовательские сценарии интерфейса

Документ описывает целевые пользовательские маршруты текущего интерфейса. Он не утверждает, что каждый маршрут прошёл браузерное тестирование: фактическая проверка отмечается отдельно в PR и чек-листе релиза.

## Принципы интерфейса

- Сохранять существующую визуальную идентичность Yugra18, включая палитру, типографику и хантыйские/мансийские орнаментальные элементы.
- Не смешивать официальные наблюдения, производные показатели, экспертные оценки и сценарные результаты.
- Не подменять отсутствующие значения нулями и не скрывать неполное покрытие.
- Сохранять исходные единицы измерения и периоды; сравнение несопоставимых рядов должно сопровождаться предупреждением.
- Не менять математические модели, источники данных или схему Supabase в рамках UX-работ.

## Сценарий 1. Быстрый переход к муниципалитету

1. Пользователь открывает карту на главной аналитической странице.
2. Находит территорию по карте или по расположенному рядом списку.
3. Наводит указатель, переводит клавиатурный фокус или нажимает на территорию.
4. Открывается паспорт выбранного муниципалитета.
5. Пользователь проверяет итоговые показатели, доступность данных по разделам, официальные наблюдения, динамику и доступные прогнозные сведения.
6. Пользователь закрывает паспорт и возвращается к исходному контексту.

Ожидаемое поведение: карта и список синхронизируют подсветку; интерактивные территории доступны мышью, касанием и клавиатурой; диалог удерживает фокус, закрывается клавишей Escape и возвращает фокус к инициировавшему элементу.

## Сценарий 2. Сравнение муниципалитетов

1. Пользователь открывает раздел сравнения.
2. Выбирает две или более территории.
3. Выбирает показатель и доступный период.
4. Сопоставляет значения, динамику и покрытие.
5. Проверяет единицы измерения и источники.
6. При необходимости экспортирует текущий срез.

Ожидаемое поведение: отсутствующие значения отображаются как отсутствующие, а не как ноль; частичное покрытие обозначается явно; несопоставимые единицы или периоды не выдаются за прямое сравнение.

## Сценарий 3. Переход от индекса к показателю

1. Пользователь изучает интегральный индекс и положение муниципалитета.
2. Переходит к компоненту или направлению индекса.
3. Изучает входящие показатели, их значения и единицы.
4. Проверяет период, территориальный уровень, источник и статус проверки.
5. Возвращается к общему индексу, сохраняя выбранную территорию.

Ожидаемое поведение: интерфейс объясняет состав показателя и не создаёт впечатления, что производный балл является исходным официальным наблюдением.

## Сценарий 4. Изучение сценарного прогноза

1. Пользователь открывает прогнозирование.
2. Выбирает муниципалитет или совокупность территорий.
3. Выбирает базовый, неблагоприятный или благоприятный сценарий.
4. Меняет горизонт и доступные сценарные параметры.
5. Сравнивает исходные значения с результатом моделирования.
6. Проверяет описание допущений и неопределённости.
7. При необходимости экспортирует сценарный результат.

Ожидаемое поведение: исходные наблюдения, параметры сценария и расчётные результаты визуально и текстово разделены. Сценарное значение не обозначается как фактическая статистика или гарантированный прогноз.

## Сценарий 5. Изучение риска

1. Пользователь открывает раздел рисков.
2. Выбирает территорию или просматривает общую картину.
3. Открывает сигнал риска.
4. Проверяет показатель, период, направление изменения, источник и объяснение.
5. Учитывает статус «недостаточно данных», если наблюдений не хватает.

Ожидаемое поведение: риск сопровождается объяснимой причиной; отсутствие данных не интерпретируется как отсутствие риска; экспертная интерпретация не маскируется под официальное наблюдение.

## Сценарий 6. Формирование отчёта

1. Пользователь открывает конструктор отчёта.
2. Выбирает охват территорий и показатели.
3. Настраивает включение сводки, графика, таблицы, методологии и отдельного слоя проверенных официальных наблюдений.
4. Просматривает предварительный вариант.
5. Экспортирует CSV или печатную/PDF-версию.
6. Проверяет, что в отчёте указаны период, единицы, источники и статусы данных.

Ожидаемое поведение: официальные наблюдения остаются отдельным слоем; демонстрационные и сценарные значения получают явные предупреждения; пустые значения сохраняются пустыми.

## Обязательные обозначения достоверности

| Тип данных | Как трактовать |
|---|---|
| Официальное наблюдение со статусом проверки | Фактическая запись из указанного источника, за указанный период и территориальный уровень |
| Производный расчёт | Результат вычисления из исходных данных; формула и входные данные должны быть доступны |
| Экспертная оценка | Интерпретация, не являющаяся официальным статистическим наблюдением |
| Сценарное значение | Условный результат модели при заданных параметрах |
| Демонстрационное/неподтверждённое значение | Не использовать как подтверждённую официальную статистику |

Для концептуальных карточек сохраняется предупреждение: «Новые карточки рассчитываются на основе существующего набора данных проекта; новые официальные статистические ряды пока не загружены».

## Критерии приёмки UX

- Нет горизонтальной прокрутки всей страницы; прокрутка таблиц ограничена соответствующим контейнером.
- Все действия доступны с клавиатуры, фокус видим и не теряется в диалогах.
- Интерактивные элементы имеют понятные доступные имена и состояния.
- Для загрузки, пустого результата и ошибки есть отдельные сообщения.
- Неизвестное значение не заменяется нулём.
- Источник, период, единица измерения и статус проверки доступны рядом с официальным наблюдением.
- CSV корректно сохраняет кириллицу, заголовки, разделители, пустые значения и статус демонстрационных данных.
- Любые визуальные изменения сохраняют палитру, типографику и культурные орнаментальные элементы Yugra18.

## Статус проверки

Документ фиксирует пользовательские сценарии и критерии приёмки. Браузерные проверки на реальных размерах экранов, проверка скачивания CSV и проверка assistive technology должны быть отмечены как выполненные только после фактического прогона.

## Автоматическая проверка согласованности карты

Перед изменениями списка муниципалитетов или геометрии карты запускайте:

```bash
npm run check:map-coverage
```

Проверка сверяет идентификаторы в `data/municipalities-detailed.json` и `src/ugraMapGeo.js`, обнаруживает отсутствующие и повторяющиеся ID. Она дополняет, но не заменяет визуальную проверку корректности контуров и подписей.
