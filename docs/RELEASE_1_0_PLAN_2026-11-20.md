# Yugra18 Release 1.0 — план завершения к 20.11.2026

**Дата фиксации плана:** 18.11.2026  
**Целевой срок:** пятница, 20.11.2026  
**Режим выпуска:** стабильный демонстрационный аналитический прототип (Release 1.0), а не валидированная прогнозная система и не подтверждённая готовность к промышленной эксплуатации.

## 1. Решение по объёму

К 20 ноября задача — не построить новую систему, а стабилизировать существующий Yugra18, проверить ключевые пользовательские сценарии и закрыть воспроизводимые блокирующие дефекты.

Оценка активной инженерной работы для такого демонстрационного релиза: **12–18 часов** при условии заморозки объёма и отсутствия крупных скрытых дефектов. Это оценка трудозатрат, а не гарантия завершения всех работ к календарному сроку.

Оценка иных уровней готовности:
- Контролируемый пилот с согласованными источниками, методикой, требованиями заказчика и проверкой на реальных процессах: ориентировочно 3–6 недель.
- Статистически валидированная прогнозная система: ориентировочно 2–4 месяца и более; срок зависит от доступности сопоставимых временных рядов, экспертного согласования и независимой проверки модели.

## 2. Обязательный объём Release 1.0

### P0 — обязательно для выпуска

1. **Стабильный запуск приложения**
   - чистая установка зависимостей, unit/regression-тесты и production build проходят;
   - нет ошибок, блокирующих открытие главных разделов;
   - глобальная Error Boundary не скрывает систематические ошибки компонентов;
   - нет критических регрессий в навигации, загрузке данных и состояниях без данных.

2. **Карта и муниципальные паспорта**
   - на карте присутствуют все 22 муниципальных образования;
   - ссылки/переходы по карте и открытие паспортов работают;
   - паспорт не подменяет отсутствие ряда нулём или выдуманным значением;
   - источники, периоды, единицы и статус данных доступны пользователю там, где они поддерживаются текущей реализацией.

3. **Данные и сравнение**
   - подтверждённые муниципальные данные отделены от поселенческих, демонстрационных и расчётных;
   - сравнение разрешено только для сопоставимых показателей, территорий, единиц и периодов;
   - отсутствующие значения остаются отсутствующими;
   - неполнота покрытия явно обозначена, а не маскируется итоговым рейтингом;
   - РИА Рейтинг используется только как внешний бенчмарк с корректным уровнем географии.

4. **Мониторинг рисков**
   - расчёт воспроизводим и не падает на пустых/неполных выборках;
   - недостаточное покрытие не превращается в зелёный статус;
   - каждый существенный сигнал объясняется доступными исходными наблюдениями;
   - пороги и веса маркируются как экспертные правила, пока не подтверждена их статистическая калибровка;
   - количество Watch/Critical не трактуется как доказательство кризиса без анализа покрытия и качества наблюдений.

5. **Сценарный прогноз**
   - три сценария и горизонты 1–3 года доступны без ошибок;
   - входные факты, экспертные шоки и рассчитанные значения визуально/текстово различимы;
   - коэффициенты и темпы, не оценённые на данных, прямо помечены как экспертные допущения;
   - неполное покрытие и неопределённость видимы;
   - запрещено называть текущий расчёт обученной, утверждённой или валидированной моделью;
   - фактический состав вычислительных входов указан явно: текущий прототип не подключает все пять проектных групп к единому расчётному ядру.

6. **Отчёты и экспорт**
   - основные сценарии формирования отчёта и CSV-выгрузки работают;
   - экспорт не объединяет муниципальные/поселенческие или официальные/демонстрационные значения в одну неразмеченную таблицу;
   - отчёт содержит дату формирования, источники/статусы доступных данных и предупреждение о границах модели;
   - PDF-экспорт считается готовым только после фактического сохранения и проверки содержимого/разбиения страниц.

7. **Подключение Supabase**
   - публичный интерфейс читает только разрешённые данные через безопасный клиент;
   - нет клиентского использования `service_role` или `sb_secret`;
   - проверены загрузка, обработка ошибок и метка последнего обновления данных;
   - текущий polling не называется мгновенным Supabase Realtime;
   - любые проверки production выполняются read-only.

8. **Доступность интерфейса**
   - существующий дизайн, орнаменты ханты и манси, карта и цветовая система сохраняются;
   - проверены широкое и узкое представления;
   - исправляются только дефекты, влияющие на работоспособность и читаемость; визуальная переделка в объём релиза не входит.

### P1 — выполнить, если не угрожает P0

- улучшить тексты пустых состояний и сообщений об ошибках;
- уточнить подписи источников и методологические предупреждения;
- добавить короткие release notes и известные ограничения;
- устранить некритические предупреждения, если для этого не требуется широкий рефакторинг.

### Не входит в Release 1.0

- полная статистически обученная и независимо валидированная модель;
- сбалансированная панель данных по всем 22 муниципалитетам и всем пяти группам;
- утверждение заказчиком окончательных весов и порогов риска;
- причинная оценка эффекта мер поддержки;
- автоматическое подключение всех выявленных источников и устранение всех пробелов каталога;
- масштабный редизайн или переписывание архитектуры;
- исправление migration drift путём переименования/удаления исторических файлов или слепого применения всех миграций;
- любые несанкционированные записи в production Supabase.

## 4. Release gates — критерии «можно выпускать»

### Автоматические проверки

Запустить в актуальной ветке:

```bash
npm ci
npm test
npm run build
npm run check:map-coverage
npm run check:risk-pilot-csv
npm run validate:rosstat-crosswalk
```

Дополнительно проверить все GitHub Actions checks конкретного PR. Не считать старый успешный workflow результатом для новых коммитов. В текущем `package.json` отдельного lint-скрипта нет — не заявлять, что lint прошёл.

### Ручная приёмка

- [ ] Главная страница загружается без runtime-ошибок.
- [ ] Все основные пункты навигации открываются.
- [ ] На карте отображены 22 муниципалитета; переходы ведут к верным паспортам.
- [ ] Паспорта корректно показывают отсутствие данных и происхождение значений.
- [ ] Сравнение не смешивает несовместимые периоды, единицы и уровни географии.
- [ ] Риск-монитор не превращает дефицит данных в зелёный статус и объясняет сигналы.
- [ ] Сценарии 1/2/3 года рассчитываются; допущения и неопределённость обозначены.
- [ ] CSV/отчёт формируются и содержат корректные подписи и caveats.
- [ ] Ошибка Supabase или отсутствие данных не ломает приложение.
- [ ] В узком viewport нет блокирующего наложения или недоступной навигации.
- [ ] PDF сохранён, повторно открыт; проверены разбиение страниц, повтор заголовков таблиц и источники.
- [ ] Production deployment, если он выполняется, соответствует проверенному SHA; URL проверен после деплоя.

**Блокирующие условия:** красный CI, сломанная навигация/карта, смешение несовместимой географии или периодов, ложный зелёный статус из-за отсутствия данных, экспорт недостоверных чисел как официальных, утечка секрета, production migration без разрешения.

## 5. Безопасность БД и известные долги

- На аудите 18.11.2026 репозиторий содержал 110 SQL-файлов, а production migration history — 96 записей; обнаружены повторяющиеся version prefixes и различия версий.
- До отдельной сверки запрещён слепой `supabase db push`, переименование и удаление старых миграций.
- Не выполнять миграции, массовые импорты, UPDATE/DELETE или изменения прав production в рамках релиза без отдельного явного разрешения пользователя.
- Успешные интеграционные миграционные тесты на disposable schema не подтверждают применение миграций к production.
- После любого разрешённого изменения production требуется отдельный readback и фиксация результата.

## 6. Правила управления объёмом

1. Любое новое пожелание после фиксации плана сначала классифицировать: P0-блокер, P1-косметика или post-release.
2. В Release 1.0 включать только P0 и P1, которые не создают риск для P0.
3. Не проводить массовый рефакторинг ради красоты кода в последние дни.
4. Не трогать стабильные визуальные решения без прямого запроса.
5. Каждое исправление должно иметь проверку: тест, воспроизводимый сценарий или ручной smoke-test.
6. После каждого логического этапа обновлять `docs/CONTINUATION_STATE.md` в checkpoint и сохранять работу в текущей ветке/PR.
7. При расхождении между сроком и качеством не скрывать дефект: зафиксировать блокировку выпуска, а не выдавать непроверенный результат за готовый.

## 7. Точная формулировка Release 1.0

> Yugra18 Release 1.0 — работающий демонстрационный аналитический прототип для 22 муниципальных образований Югры. Основные пользовательские сценарии прошли автоматические и функциональные проверки; доступность статистических данных неоднородна; часть индексов, порогов и сценарных коэффициентов имеет экспертный/концептуальный характер. Система не является официальным прогнозом, не заменяет проверку первичных данных или управленческое решение и не заявляется как промышленно валидированная система.

Не использовать формулировки «полностью готовая промышленная система», «точный прогноз», «модель доказала точность» или «пилот валидирован», пока это не подтверждено отдельными доказательствами.
