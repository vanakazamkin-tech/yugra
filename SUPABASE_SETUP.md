# Подключение Yugra к двум проектам Supabase

Приложение объединяет два независимых проекта Supabase. Обе базы содержат муниципальные статистические наблюдения; первая — исходный массив и паспортные реестры, вторая — продолжение загрузки, новые показатели и staging. Это не master/replica по всей схеме: данные объединяются в приложении по муниципалитетам, показателям, периодам и источникам.

## 2. Как приложение объединяет базы

- Справочник муниципалитетов читается из обеих баз и объединяется по `municipality.id`; локальный JSON остаётся резервом для концептуальных полей.
- Каталоги `data_sources` объединяются по `id`.
- `municipality_indicators` читается из обеих баз; точные совпадения схлопываются по муниципалитету, коду показателя, году, периоду, географии, единице и источнику.
- `municipal_program_execution` читается из обеих баз и объединяется по муниципалитету, источнику, коду программы и отчётной дате.
- Дополнительные паспорта, инвестплощадки, учреждения, инвестпроекты, предприятия, инфраструктура, участки, топливо и внешние рейтинги читаются из DB1.
- Временная недоступность одной базы не должна скрывать доступные данные другой.

Ни одна из двух баз не объявляется единственным хранилищем статистики. Не удаляйте строки из одной базы ради копирования в другую.

## 3. Переменные окружения

В `.env.example` приведены имена переменных. Для локальной разработки скопируйте его в `.env.local` и заполните две пары публичных ключей:

- `VITE_SUPABASE_CORE_URL` и `VITE_SUPABASE_CORE_ANON_KEY` — DB1;
- `VITE_SUPABASE_DATA_URL` и `VITE_SUPABASE_DATA_ANON_KEY` — DB2.

Все четыре переменные добавлены в Vercel для Production, Preview и Development. Старые `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` временно поддерживаются как fallback для DB1.

Используются только publishable/anon ключи. Никогда не помещайте `service_role` / `sb_secret_...` в `VITE_*`, браузерный код или клиентские переменные Vercel.

## 4. Справочники и внешние ключи

В обеих базах присутствуют те же 22 муниципальных ID. В DB1 перенесены 30 source ID из DB2; при этом DB1 сохраняет и собственные источники. Для будущих новых записей можно выполнить локальную команду:

```bash
npm run sync:supabase-reference
```

Скрипт зеркалирует только ID и названия/описания справочников из DB2 в DB1. Он не копирует строки `municipality_indicators` и не удаляет собственные источники DB1. Для запуска нужны локальные `SUPABASE_CORE_SERVICE_ROLE_KEY` и `SUPABASE_DATA_SERVICE_ROLE_KEY`; они не используются клиентским приложением и не добавляются в Vercel.

## 5. Распределение файлов

- `public/images/` — изображения и орнаменты для браузера.
- `public/data-dictionary.md` — публичная копия словаря данных.
- `data/municipalities-detailed.json` — резервный набор Vite, импортируемый как модуль; он остаётся в `data/`, потому что перенос в `public/` потребовал бы менять загрузчик.
- `data/rosstat/` — шаблоны и материалы подготовки статистических выгрузок.
- `supabase/audits/`, `supabase/imports/`, `supabase/manual_imports/`, `supabase/migrations/`, `supabase/statistics/migrations/`, `supabase/tests/` — SQL, загрузочные и проверочные материалы; не переносить в публичную статику.
- `docs/`, `scripts/` — документация и локальные инструменты обработки.

Не перемещайте файлы сборки, импорта и диагностики в `public/` без изменения кода: это может нарушить пути загрузки и раскрыть внутренние материалы.

## 6. Обновление

- Справочник муниципалитетов читается из обеих баз при запуске и далее опрашивается раз в 60 секунд.
- Каталоги источников, показатели и исполнение программ читаются из обеих баз раз в 5 минут.
- Паспортные наборы и рейтинги читаются из DB1.
- Резервный локальный JSON используется до первой успешной загрузки справочников.
- Данные со статусом `needs_review` не должны попадать в публичные аналитические выводы.
