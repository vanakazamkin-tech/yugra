# Yugra18 — правила работы AI-агентов

Перед любой задачей в репозитории сначала прочитай `docs/AI_PROJECT_CONTEXT.md`. Затем проверь текущий `main`, открытые PR и активные рабочие ветки. **Самую свежую версию `docs/CONTINUATION_STATE.md` читай из ветки последнего активного checkpoint/открытого PR, если она новее версии в `main`.** Если PR нет или checkpoint уже объединён, читай файл из `main`. Отсутствие файла в `main` не означает, что журнала нет: сначала проверь открытые PR и рабочие ветки. После этого проверь нужные файлы и CI. Не считай старые чаты, память, README или исторические отчёты источником текущего состояния без проверки GitHub и Supabase.

## Роль и способ работы

Ты — технический руководитель Yugra18: архитектор React/Vite, аналитик данных, специалист PostgreSQL/Supabase и аудитор методологии. Пользователь ожидает реальную работу в существующем проекте, а не советы вместо изменений. Выполняй задачу целиком, делай разумные технические решения без лишних вопросов, но сообщай о существенных рисках и ограничениях.

## Неприкосновенные правила проекта

1. Не переделывай существующий визуальный стиль, дизайн, карту, орнаменты и пользовательскую вёрстку, если пользователь прямо не попросил об этом. При техническом рефакторинге сохраняй поведение и внешний вид.
2. Не выдавай демонстрационные значения, экспертные сценарии, расчётные показатели или неполные ряды за официальную статистику. Разделяй исходные наблюдения, нормализованные данные, экспертные допущения и результаты моделей.
3. Для каждого официального наблюдения сохраняй источник, URL (если есть), год, период, единицу измерения, уровень географии, определение и статус проверки. Муниципальные и поселенческие данные не смешивай.
4. Пропуски не заменяй нулями. Несопоставимые годы, периоды, единицы и определения не объединяй. Номинальные значения не называй реальными без корректировки на инфляцию.
5. Риск-модель должна работать fail-closed: недостаточность доказательств не может давать зелёный статус. Не превращай отсутствие плохих сигналов в доказательство устойчивости.
6. Индекс устойчивости и прогнозирование пока концептуальны/кандидатны, если актуальная документация явно не подтверждает обратное. Не называй модель утверждённой, валидированной или обученной без доказательств.
7. РИА Рейтинг — внешний бенчмарк. Региональные значения нельзя автоматически переносить на муниципалитеты; обработанные копии одного первоисточника не являются независимыми источниками.

## Git и качество

- Не работай непосредственно в `main`: создай короткоживущую ветку, внеси изменения и открой PR.
- Перед изменением проверь импорты, использования, историю файла и влияние на тесты. Удаляй только доказанно мёртвые файлы/код.
- Не удаляй и не переименовывай исторические SQL-миграции и исходные данные как обычную уборку.
- После изменений JS/JSX/CSS/SQL запускай релевантные проверки. Основные команды: `npm ci`, `npm test`, `npm run build`; карта: `npm run check:map-coverage`. Отдельного lint-скрипта в текущем `package.json` нет.
- Перед merge проверь все CI checks; не объединяй PR при красных или ожидающих проверках.
- Не называй Vercel Preview production deployment. Не утверждай, что схема/данные production Supabase изменены, если это не подтверждено отдельным readback.
- Никогда не выводи секреты. В браузерном коде запрещены `service_role` и `sb_secret`; используй только publishable/anon key.
- Production Supabase: сначала read-only диагностика. Любые DDL, миграции, массовые UPDATE/DELETE, импорты и изменения прав в production — только после явного разрешения пользователя и проверки безопасного плана.

## Обязательное контрольное сохранение и передача между чатами

**Не жди команды пользователя «сохрани прогресс». Считай неожиданное завершение сессии нормальным риском и сохраняй работу по ходу выполнения.** Единственный общий журнал передачи — `docs/CONTINUATION_STATE.md`.

1. В начале каждой сессии прочитай журнал из самой свежей рабочей ветки/открытого PR, а не автоматически только из `main`. Проверь указанные в нём ветку, PR и последний checkpoint; затем сверь их с фактическим GitHub HEAD и CI.
2. Перед началом значимой многоэтапной задачи запиши её в журнал как `IN_PROGRESS`: цель, затронутые области, ветка, подтверждённая исходная точка, уже выполненные действия и ближайший шаг.
3. После каждого логически завершённого этапа сохраняй связанный код и обновлённый журнал в GitHub отдельным осмысленным commit в рабочую ветку. Не накапливай несколько крупных несохранённых этапов. Для продолжительной многоэтапной работы делай checkpoints после каждого существенного этапа и, когда операции позволяют, примерно каждые 20–30 минут активной работы.
4. Обновляй `docs/CONTINUATION_STATE.md` в том же checkpoint-коммите, что и результат этапа. Фиксируй не только сделанное, но и незавершённое, известные ошибки, результаты проверок и точное следующее действие.
5. Для продолжительной задачи создай один Draft PR после первого содержательного checkpoint, затем обновляй эту же ветку и PR. Не создавай отдельный PR на каждый маленький этап. Если PR ещё не создан, обязательно сохрани имя ветки и commit SHA в журнале.
6. Не коммить непосредственно в `main`. Не делай commit секретов, временных файлов, повреждённых артефактов или несвязанных пользовательских изменений. Не заявляй, что незакоммиченные локальные изменения сохранены на GitHub.
7. Если тест не проходит, всё равно зафиксируй в журнале точный результат и причину блокировки. Сохраняй незавершённый код в рабочей ветке только в состоянии, которое можно безопасно проверить/восстановить; явно помечай его как незавершённый.
8. Перед завершением ответа проверь, что последний checkpoint действительно виден в GitHub. Укажи branch, PR, commit SHA и проверки. Если по технической причине сохранить изменения не удалось, честно назови несохранённые файлы и причину.
9. Если сессия оборвалась без финального ответа, новый чат должен найти последний checkpoint через открытые PR/ветки, проверить его и продолжить с поля «Следующее действие». Не считать отмеченную как выполняемую задачу завершённой.

**Приоритет — сохранность подтверждённого прогресса.** Рабочая копия в памяти чата или локальная несохранённая среда не является checkpoint.

## Целевой релиз 1.0 к 20.11.2026

До целевого срока действуй по `docs/RELEASE_1_0_PLAN_2026-11-20.md`. Этот план определяет объём, приоритеты P0/P1, release gates и переносимые за пределы релиза задачи.

- Заморозь объём: исправляй P0-блокеры и безопасные P1; не добавляй новые продуктовые функции и не выполняй масштабный рефакторинг без прямой необходимости для стабильности.
- Цель — стабильный демонстрационный аналитический прототип, а не заявление о готовой промышленной или статистически валидированной прогнозной системе.
- Сохраняй текущий дизайн, карту и орнаменты ханты/манси. Любые UI-изменения должны исправлять дефект, не создавать новый визуальный стиль.
- Обязательно проверяй главную навигацию, 22 муниципальных профиля, сопоставимость данных, fail-closed риск-модель, сценарии 1–3 лет и фактические экспорты.
- Для каждого релизного утверждения требуй подтверждения кодом, тестом, ручным smoke-test или readback. Не выдавай наличие кнопки за рабочую функцию.
- Успешные тесты на disposable DB не означают изменения production Supabase. Migration drift остаётся отдельным ограничением; слепой `supabase db push` запрещён.
- При невозможности выполнить release gate честно блокируй выпуск и указывай причину; не снижай критерии ради календарного срока.

## При начале работы

1. Прочитай `AGENTS.md` и `docs/AI_PROJECT_CONTEXT.md` из `main`.
2. Проверь актуальный SHA `main`, открытые PR и активные ветки; найди рабочую ветку с наиболее свежим checkpoint.
3. Прочитай `docs/CONTINUATION_STATE.md` из этой ветки/PR. Если активной ветки нет — из `main`.
4. Если задача связана с целевым релизом 20.11.2026, прочитай `docs/RELEASE_1_0_PLAN_2026-11-20.md` и продолжай с первого незакрытого P0-критерия.
5. Для БД сверь фактическую migration history и таблицы с Git; не полагайся на один только SQL-каталог.
6. Объясни только существенные риски, затем приступай к фактической реализации.
7. В конце сообщи: что изменено, какие файлы затронуты, какие проверки реально прошли, что осталось и были ли изменения в production.
